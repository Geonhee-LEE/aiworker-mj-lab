## 1) GJK/narrow-phase 심플렉스 워밍스타트 — 적용 불가 (negative finding)

물리 엔진 커뮤니티(Bullet/GameDev.net 스레드)에서 반복적으로 보고되는
최적화: 연속된 인접 configuration 사이에서는 GJK 심플렉스를 이전 쿼리의
결과로 초기화하면("temporal coherence") narrow-phase가 support-point 호출
1회 만에 수렴하는 경우가 많다 — RRT/PRM/EST처럼 수천~수백만 번의 근접
충돌 쿼리를 요구하는 sampling-based planner에 이론적으로 잘 맞는 아이디어.

**이 저장소에는 적용 불가능하다.** `.venv`의 실제 mujoco 3.12.0 바인딩을
확인한 결과:

```
mj_geomDistance(m, d, geom1, geom2, distmax, fromto) -> float
```

워밍스타트/심플렉스/GJK 관련 심볼이 파이썬 바인딩에 전혀 노출되지 않는다
(`[n for n in dir(mujoco) if 'warm' in n.lower() or 'gjk' in n.lower() or
'ccd' in n.lower()]` → `[]`). `mj_collision`/`mj_geomDistance` 둘 다
narrow-phase 내부 상태를 呼출부에 반환하거나 입력받는 매개변수가 없다 —
MuJoCo가 내부적으로 무엇을 쓰든(libccd 계열 추정) C API 밖으로 노출하지
않는다. 이 기법을 적용하려면 MuJoCo 엔진 자체를 패치하거나 별도 GJK
구현을 직접 들여와야 하는데, 둘 다 PRD §7 "기존 자산 재사용 우선"(엔진
재구현 금지) 원칙과 정면 충돌한다. `collision_state.py`의 기존 설계
철학(엔진의 broad-phase를 그대로 쓰고 margin만 조작 — docstring 1~9행)과도
맞지 않는다.

이 발견은 MP-0028(safety-certificate 캐싱, feed 005)과 결이 다르다 —
safety-certificate는 우리 코드 레이어(호출 빈도 자체를 줄임)에서 구현
가능했지만(다만 순이득이 불확실해 보류), GJK 워밍스타트는 애초에 엔진
내부 레이어라 우리 코드에서 손댈 지점이 없다. **신규 TODO 없음** — 막다른
길로 기록만 남긴다(향후 동일 주제 재조사 방지).

## 2) MJX(MuJoCo XLA) 기반 배치 병렬 충돌검사/샘플링 — 신규 조사 후보

MJX는 MuJoCo 공식 JAX 네이티브 변형으로, 충돌검사·제약해석을 포함한
전체 시뮬레이션을 XLA 프리미티브 그래프로 표현해 GPU에서 배치 병렬 실행
가능하게 만든다. 2025년 이후 문헌(GMT*, VAMP, pRRTC, Kino-PAX 등)은 이런
배치 병렬 충돌검사를 이용해 고차원 configuration space에서 밀리초 단위
계획을 보고한다 — 우리 저장소의 병목(`is_valid()`가 매 샘플마다 순차
`mj_kinematics`+`mj_collision` 1회, MP-0004/0017 실측 12.5ms 계획 시간
자체는 이미 예산 500ms 대비 여유 있지만, 더 어려운 장면·narrow_passage류
(MP-0031 실측 성공률 78-88%로 하락)에서는 샘플 수 자체를 늘려야 할 수
있음)와 구조적으로 맞닿아 있다.

VAMP-MR(MP-0025)·hydrax(MP-0021)와 같은 "GPU 가속 후보, owner=user"
버킷으로 분류하되 **성격이 다르다**는 점을 명시해 둔다:

- VAMP-MR: OMPL 의존 C++ 빌드, PRD Non-Goal(OMPL 명시 제외)과 정면 충돌
  (feed 003 이미 확인).
- hydrax: 실행 레이어(P3) MPPI 제어, 전역 계획과는 다른 층.
- **MJX**: 이미 이 저장소가 쓰는 MuJoCo 엔진의 공식 배치/미분가능 변형
  이라 "외부 플래닝 라이브러리"(OMPL류) Non-Goal에는 안 걸리지만, JAX
  전이 의존성(CUDA/XLA 빌드 체인)이 새로 들어오고 `is_valid`/`clearance`
  전체를 배치 텐서 연산으로 다시 써야 하는 대규모 구조 변경이라 여전히
  사람의 아키텍처 판단이 필요하다.

**신규 TODO 1건**(owner=user, P5) — 구현 여부가 아니라 "도입 검토" 자체를
사람 판단 대기로 등록한다(hydrax/VAMP-MR/BIT*와 동일 패턴).
