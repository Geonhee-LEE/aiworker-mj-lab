## 1. PRD 공백 확인

`docs/prd.md:15` 실행 안전성 행: "재생 중 최소 clearance ≥
`whole_body_ik.collision_safe_distance_m`(0.01) — 미측정". 저장소 전체를 확인한 결과:

- `ArmCollisionChecker.clearance(q)`(`planning/collision_state.py`)는 이미 있고
  `clearance_report_m=0.20` 상한까지 정확한 최소 signed distance를 준다("벤치마크용").
- 그러나 이 함수를 **경로/궤적 위에서 호출하는 곳이 없다** —
  `tests/test_planning_execution.py`는 최종 site 오차만, `scripts/benchmark_planning.py`는
  성공률·시간·길이만 기록. `clearance`가 등장하는 건
  `profile_certificate_caching.py`(캐싱 순이득 프로파일링)뿐이다.
- TODO에도 이걸 다루는 항목이 없다. MP-0041(resolution_rad 완결성)은 **이론적 상한**을
  단위 테스트로 확인하는 것이고, MP-0035는 `clearance()`의 Jacobian 낭비 제거다 — 둘 다
  "경로 위 실측"은 아니다.

## 2. 왜 실측이 필요한가 (MP-0041과의 관계)

`is_valid`는 `padding_m`(0.012)만큼 margin을 부풀려 판정하므로, **검사된 표본**에서는
실제 거리 ≥ ~0.012m가 구성상 보장된다. 그러나 (a) 표본 사이(EdgeChecker
`resolution_rad=0.05` 간격)와 (b) shortcut/시간 파라미터화 이후의 보간점에서는 보장이
없다. 016은 이걸 이론 상한으로 지적했고, 여기서 빠진 것은 **경험적 반증/확인**이다:
계획·평활화된 경로를 검사 간격보다 훨씬 촘촘히(예: 0.005 rad) 재표집해 `clearance()`의
최솟값을 시나리오(장애물 없음/narrow_passage/cluttered)별·seed별로 기록하면,

- 최솟값이 항상 padding 근처 이상이면 → MP-0041 위험은 현 장면에서 실재하지 않음(근거 확보,
  PRD 행을 "✅ 실측"으로 갱신 가능).
- narrow_passage에서 `< collision_safe_distance_m`(0.01)이 나오면 → 실제 결함 증거,
  MP-0041의 `resolution_rad` 하향이 정당화됨.

어느 쪽이든 PRD 표의 유일한 미측정 칸을 채운다. 새 알고리즘 없이 기존 `clearance()` +
`benchmark_planning.py` TSV 컬럼 1개(`min_clearance_m`)로 가능하다.

## 3. 구현 스케치 (executor용, 미검증)

- 재표집은 `shortcut_path`/`time_parameterize` 결과 경로의 각 세그먼트를 관절공간 선형
  보간으로 촘촘히 나눈다(실행 모듈이 쓰는 보간과 동일해야 의미 있음 — `execution.py`가
  실제로 선형 보간 궤적을 재생하는지 먼저 확인).
- `clearance()`는 `is_valid`보다 훨씬 비싸다(feed 002/009). 경로당 수백 점 × 50 seed는
  벤치마크 2분 예산을 넘길 수 있으니 `--seeds`를 줄이거나 별도 스크립트로 두고,
  MP-0035(need_gradient=False)가 병합돼 있으면 그 위에서 돌리는 게 유리하다.
- `clearance()`는 `clearance_report_m` 밖이면 `inf`를 반환하므로 TSV엔 `inf`를 상한
  0.20으로 클립해 기록(집계 오염 방지).

## 4. `mj_geomDistance` 센티널 버그 점검 (부정적 결과 — 조치 불필요)

검색에서 google-deepmind/mujoco 이슈 #2710을 확인: 파이썬 바인딩 3.3.3에서 거리 상한 안에
충돌이 없으면 문서와 달리 `distmax`가 아니라 **DBL_MAX(~1.8e308)** 를 반환한다(이슈
open 상태로 확인, 수정/우회 미기재). `kinematics/collision.py::collision_distance_gradient`를
읽어 보니 `raw_distance >= max_distance - 1e-12 and segment_length < 1e-12`로 걸러내고,
추가로 `distance > max_distance`도 `None` 처리하므로 **두 동작 모두에 안전**하다. 이슈
#1784(sphere-hfield 음수 거리)는 이 저장소가 hfield를 쓰지 않아 해당 없음. 로컬 환경에는
`mujoco`가 설치돼 있지 않아(이 셸 기준) 실제 버전은 재확인하지 못했다 — 코드 실독 결론이다.
