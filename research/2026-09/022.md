# 022 — `_Tree.nearest`/`near`의 순수 파이썬 선형 탐색이 RRT*의 고정 시간 예산을 잠식하고 있을 가능성

_cycle: 2026-09-22 · researcher_

## 배경

PR 큐 4건(#18~#21) 포화 10일째. 충돌검사·샘플링·후처리 각도는 001~021에서 대부분
소진돼, 이번엔 지금까지 한 번도 안 본 **최근접 이웃(NN) 탐색 비용**을 코드·실측
데이터와 대조했다. (RRT-Connect 쪽 tree balancing/swap 변형도 함께 확인 — 아래 §4.)

## 1. 코드 확인

- `rrt_connect.py:52-60`, `rrt_star.py:48-62`의 `_Tree.nearest`/`near`는
  `for node in self.nodes: space.distance(node, point)` 형태의 파이썬 루프다.
  `space.distance`(`arm_state.py:101`)는 호출마다 `np.asarray`×2 + `np.linalg.norm`을
  부르므로 노드당 고정 오버헤드가 크다.
- `docs/guide/motion-planning.md:48`은 "7-D·수천 노드 규모에서는 충분히 빠르다(§성능
  참고)"라고 주장하지만, 저장소 전체(research/journal/results/TODO)에서 이 비용을
  **측정한 기록이 없다**(`nearest`/`KD-tree` grep 결과 docs 서술뿐).
- `.nodes`는 호출부에서 `tree.nodes[i]` 인덱싱으로만 쓰인다
  (`rrt_connect.py:87,161`, `rrt_star.py:183,197-210`) — 내부 저장소를 바꿔도 호출부
  영향이 작다.

## 2. 격리 마이크로벤치 (저장소 코드 미수정, 독립 스크립트)

7-D 균등 무작위 노드, 현재 구현과 동일한 루프 vs `argmin(einsum(diff,diff))`:

| N | 루프 | 벡터화 | 배율 |
|---|---|---|---|
| 200 | 0.271 ms | 5.5 µs | 49× |
| 2000 | 2.73 ms | 26.8 µs | 102× |
| 5000 | 6.76 ms | 102.5 µs | 66× |

루프는 약 **1.35 µs/노드**. 결과 인덱스는 세 크기 모두 루프와 일치(assert 통과).

## 3. 실측 데이터와의 정합성 (추정 — 프로파일링 필요)

`results/p5-planner-comparison.tsv`의 RRT*(장애물 없음): 시간 예산 15 s에 `iterations`가
seed마다 **3065~3084로 거의 상수**, 즉 반복당 약 4.9 ms. 누적 `checks` 차분으로 보면
반복당 충돌검사는 ~8회, RRT-Connect 실측(92 checks/14 ms ≈ 0.15 ms/check, 오버헤드
포함 상한) 기준 검사 비용은 반복당 ≲ 1.2 ms. 남는 ~3.5 ms는 반복당 `nearest`+`near`
= 2회 선형 스캔 × 평균 트리 크기 ~1500 × 1.35 µs ≈ 4 ms와 크기가 맞는다.

→ **가설**: RRT* 벽시계 시간의 절반 이상이 NN 스캔이고, "반복 수가 시간 예산으로
상한되는" 구조라 스캔이 빨라지면 같은 15 s에 몇 배 더 많은 표본을 얻는다. 반복 수가
거의 상수라는 사실 자체가 시간이 검사 횟수(seed마다 달라짐)가 아닌 트리 크기에 지배됨을
시사한다. 단 `checks`당 비용 0.15 ms는 다른 시나리오 값이라 **cProfile로 확인이
선행돼야 한다**(확정 아님).

**P5 결론에 미치는 영향**: MP-0031이 낸 "narrow_passage/cluttered에서 RRT* 성공률
78-88%"는 알고리즘 한계일 수도, 예산 내 표본 부족(NN 병목)일 수도 있다. 후자면 MP-0032
(bridge test)·MP-0039(direct ellipsoid sampling)·MP-0044(Halton)의 효과 측정도
같은 오염 위에서 이뤄진다 — NN 가속이 그것들의 A/B 기준선이 된다.

## 4. 함께 점검했으나 조치 없음

- **RRT-Connect**: 벤치 중앙값 12.5 ms·트리 소형이라 NN 비중이 작다(iterations=1
  사례 다수). 벡터화해도 이득이 미미하므로 대상에서 제외 — 공통 자료구조를 쓰게 되면
  덤으로 적용될 뿐.
- **trees swap**: 현재 매 반복 무조건 교대(`rrt_connect.py:170`). 문헌(Improved
  RRT*-Connect, Sensors 2025 등)에 "작은 트리를 우선 확장" 변형이 있으나 이 장면에서
  100% 성공·12.5 ms라 튜닝 유인이 없다(017과 같은 결론).
- **goal_bias 스왑 시**: `sample = goal`이 goal 트리 자신의 루트를 향해 확장돼
  중복 노드 1개가 추가되지만 이어지는 CONNECT가 시작 트리를 goal로 뻗는 유효한 시도라
  기능 결함은 아니다.
- **KD-tree**: 문헌은 차원 ~20 이상에서 KD-tree≈브루트포스라 하고 7-D는 애매한 구간,
  게다가 SciPy 등 의존성 추가는 §1 비-목표(외부 플래닝 라이브러리 도입 금지)의 취지와 어긋날 소지가 있고(SciPy는 플래닝 라이브러리는 아니므로 엄밀한 위반은 아님) 설치 요건도 늘린다. PRD §7의 "+50 LOC 이상이면 측정 가능한 이득 명시" 기준상 벡터화는 ~20 LOC 규모다. 브루트포스를
  벡터화하는 것이 의존성 없이 가장 싸다.

## 5. 제안 (구현은 executor)

1. **선행 측정**: `plan_rrt_star`를 cProfile로 돌려 `nearest`+`near`의 누적 시간 비중
   보고(기록만, 코드 수정 없이 임시 스크립트).
2. 비중이 크면 `_Tree`를 용량 배가식 `ndarray` 버퍼(`_points[:n]`)로 바꾸고
   `nearest = argmin(einsum('ij,ij->i', d, d))`, `near = flatnonzero(sq <= r*r)`.
   `.nodes[i]` 인덱싱 호환을 위해 `nodes`는 행 뷰를 돌려주는 얇은 프로퍼티로 유지.
3. **결정성 주의**(R-NF-005): `argmin`은 첫 최소값을 돌려주므로 루프의 엄격한 `<`와 동일한
   동률 처리다. 다만 `norm`(sqrt) 대신 제곱합 비교라 부동소수 경계(`near`의 `<= radius`)
   에서 극히 드물게 결과가 갈릴 수 있다 → 기존 seed 몇 개로 경로 동일성 확인 후, 예산
   기반이라 반복 수가 늘어 RRT* 결과가 바뀌는 것은 정상이므로 `results/`는 재측정으로 새
   행을 추가(append-only).
4. 적용 후 MP-0031 narrow_passage/cluttered RRT* 성공률 재측정 → PRD P5 결론 갱신 여부는
   사람 판단(이 노트는 결론을 바꾸지 않음).
