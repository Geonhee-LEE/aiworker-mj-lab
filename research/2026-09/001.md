## 1) 벤치마크 하네스 설계 (MP-0013에 직접 적용)

출처: OMPL Planner Arena / MotionBench 계열 문헌, "Robot motion planning
benchmarking and optimization" 계열 서베이.

- **주 지표는 성공률(고정 시간예산 내)** — 계획 시간 자체보다 "예산 안에 풀렸는가"가
  1차 지표여야 한다는 게 공통 관례. 우리 PRD의 "median ≤ 500ms" 기준과 별개로,
  TSV에는 반드시 `success`(bool) 컬럼을 success rate 집계가 바로 되게 남겨야 한다
  (이미 `MP-0018 aggregate_results.py`가 존재하므로 이 컬럼 명세만 맞추면 됨).
- **중앙값 하나로는 부족, 분포를 남겨라** — OMPL Planner Arena는 box plot/CDF로
  median·quartile·outlier를 같이 본다. `benchmark_planning.py`가 TSV에 매 seed의
  `planning_time_s`를 개별 행으로 남기면(집계는 aggregate 단계에서), 나중에
  percentile/CDF를 재계산할 수 있다 — 지금 미리 mean만 내고 raw를 버리면 나중에
  못 되돌린다.
- **factorial 원칙 — 변수 하나씩만 바꿔라** — "baseline vs shortcut", "baseline vs
  time_parameterize"처럼 한 실행에서 한 변수만 켜고 나머지는 고정해야 MP-0007
  같은 전/후 비교가 통계적으로 의미 있다. seed 목록과 장면 설정을 두 실행 사이에
  절대 다르게 하지 말 것 — 지금 `demo_plan_right_arm.py --seed N`이 이미 결정론적
  이므로 그대로 재사용 가능.
- **병렬 실행 시 시드 함정** — 여러 프로세스를 동시에 띄우면 "현재 시각" 기반
  시드가 겹칠 수 있다는 경고가 반복적으로 나온다. 우리는 이미
  `np.random.default_rng(seed)`로 seed를 명시 전달하므로(R-NF-005) 해당 안 됨 —
  단, 향후 벤치마크를 GNU parallel 등으로 병렬화할 계획이 생기면 seed를 프로세스
  인자로 명시 전달하는 지금 방식을 유지해야 한다는 점만 기록.

## 2) 실행 모듈 속도 feedforward (MP-0008/MP-0009에 참고)

출처: 로봇팔 궤적 추종 PD+feedforward 비교 문헌 다수(steady-state error 분석
기반 feedforward, velocity feedforward+PID 등).

- 여러 문헌에서 공통적으로, **위치 PD만으로는 궤적을 "따라가는" 구간에서 항상
  위상 지연(lag)이 남고**, 목표 속도를 feedback 루프에 직접 더하는
  velocity feedforward가 추종 오차를 크게 줄인다(문헌에서는 베이스라인 대비
  30~50%대 개선을 보고하지만, 우리 모델·이득에서 그대로 재현된다는 보장은 없음 —
  수치는 참고용).
- 현재 `ArmTorqueController.apply(data, q_des, kp_scale)`
  (`src/ffw_sh5_grasp/control/arm.py:83`)는 `tau = qfrc_bias + kp*(q_des-q) -
  kd*qd`로, **목표 속도를 받지 않는다** — 정적 자세 유지(Phase 3 grasp)에는
  맞지만, 궤적을 실시간으로 쫓아가는 P3 planning 실행에는 `-kd*qd` 항이 목표
  속도가 0이라고 암묵적으로 가정하는 셈이다.
- MP-0008 구현 시 고려할 옵션(택 1, 결정은 executor 몫):
  (a) `apply()`에 선택적 `qvel_des=None` 인자를 추가해 `- kd*qd`를
      `+ kd*(qvel_des - qd)`로 바꾸고 기본값 0으로 하위 호환 유지 — 이러면
      `Trajectory`가 시간 파라미터화 과정에서 이미 갖고 있을 구간별 관절
      속도(세그먼트 기울기)를 그대로 흘려보낼 수 있음.
  (b) `execution.py`에서 `q_des(t)`만 보간하고 컨트롤러는 그대로 두되, 최종
      site 오차 5 mm 기준을 만족하는지 먼저 측정해보고 안 되면 그때 (a)를 적용.
  PRD 성공 기준이 "최종(정지) 오차 ≤5mm"라 궤적 추종 중 과도 오차는 명시 요구사항이
  아니므로, (b)로 먼저 재는 게 `+50 LOC` 정당화 기준(단순성 헌법)에 더 맞다.

## 3) 충돌 검사 가속 — 조사했으나 액션 없음

`mj_geomDistance` 관련 문헌은 "buffer allocation 오버헤드"와 "학습 기반 proxy
collision"을 언급하지만, 우리 `ArmCollisionChecker.is_valid`는 이미
`mj_kinematics`+`mj_collision`(엔진 broad-phase, margin 부풀리기)만 쓰고
`clearance()`(비싼 exact 계산, `collision_distance_gradient`)는 벤치마크
리포팅에만 쓴다 — 이는 문헌이 권장하는 "빠른 boolean 체크 / 비싼 정확 거리
분리" 패턴과 이미 일치한다. 새 TODO 없음.
